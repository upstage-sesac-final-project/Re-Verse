# Re-Verse 맵 생성 및 안전 좌표 보정 시스템 기술 백서

본 문서는 Re-Verse 프로젝트의 핵심 엔진인 **LLM 기반 설계와 파이썬 기반 룰베이스 검증**의 결합 원리를 상세히 설명합니다. 특히 플레이어가 지형에 갇히는 문제를 해결하기 위한 비트연산 및 알고리즘적 접근법을 다룹니다.

---

## 1. RPG Maker MZ 비트마스크 상세 해석 (`tile_checker.py`)

RPG Maker MZ에서 타일의 '성격'은 타일셋 파일의 `flags` 배열에 저장된 16비트 데이터를 통해 결정됩니다. 우리 시스템은 이 데이터를 0과 1의 비트 단위로 쪼개어 지형의 물리적 특성을 완벽히 재현합니다.

### 1.1 비트별 물리적 의미 (Bit-level Analysis)
각 비트는 특정 방향의 통행 가능 여부나 타일의 특수 속성을 의미합니다.

| 비트 값 | 명칭 | 기술적 상세 설명 |
| :--- | :--- | :--- |
| **0x01** | `IMP_DOWN` | 캐릭터가 현재 타일에서 **아래쪽**으로 나가는 것을 차단합니다. |
| **0x02** | `IMP_LEFT` | 캐릭터가 현재 타일에서 **왼쪽**으로 나가는 것을 차단합니다. |
| **0x04** | `IMP_RIGHT` | 캐릭터가 현재 타일에서 **오른쪽**으로 나가는 것을 차단합니다. |
| **0x08** | `IMP_UP` | 캐릭터가 현재 타일에서 **위쪽**으로 나가는 것을 차단합니다. |
| **0x10** | `FLAG_STAR` | '지붕'이나 '나무 꼭대기' 타일입니다. 캐릭터가 아래로 지나갈 수 있으며 통행 판정은 아래 레이어에 위임합니다. |
| **0x100** | `FLAG_DAMAGE` | 독늪이나 용암 타일입니다. `is_walkable` 로직에서 안전한 스폰 지점을 찾을 때 이 타일은 자동으로 배제됩니다. |

**[핵심 코드: 비트 연산 판정]**
```python
# 하위 4비트(0x0F) 중 하나라도 켜져 있으면 특정 방향이 막힌 타일입니다.
# 시작 좌표로는 사방이 뚫려있는(flag & 0x0F == 0) 타일이 가장 안전합니다.
is_blocked = (tile_flag & 0x0F) > 0
```

### 1.2 4중 레이어 중첩 및 암흑(Void) 판정
RPG Maker MZ의 맵은 레이어 0(바닥)부터 레이어 3(장식)까지 4개의 층으로 구성됩니다.
1. **상위 레이어 우선 원칙**: 시스템은 레이어 3 → 2 → 1 → 0 순서로 검사합니다. 가장 먼저 발견되는 '공기가 아닌 타일'이 해당 칸의 통행성을 결정합니다.
2. **투명 타일 처리**: 레이어 값이 `0`인 칸은 투명(Empty)한 곳입니다. 시스템은 해당 칸을 건너뛰고 바로 아래 레이어를 확인합니다.
3. **암흑(Void) 맵 방지**: 만약 특정 좌표의 **모든 레이어(0~3)가 0**이라면, 그곳은 타일이 아예 배치되지 않은 '새까만 빈 공간'입니다. 시스템은 이를 **절대 통행 불가**로 판정하여 플레이어가 맵의 경계 밖으로 탈주하는 것을 물리적으로 차단합니다.

## 2. BFS 기반 좌표 재배정 알고리즘

### 2.1 도입 배경: 왜 BFS(너비 우선 탐색)인가?
LLM(대규모 언어 모델)은 맵의 전체적인 구도와 이벤트 배치는 잘 설계하지만, **특정 좌표(X, Y)가 물 타일(통행 불가)인지 땅 타일(통행 가능)인지까지는 정확히 알지 못합니다.**
- **문제**: LLM이 워프 좌표를 물 한가운데나 벽 속에 배치하면 플레이어는 움직일 수 없는 '소프트락' 상태에 빠집니다.
- **해결**: LLM이 준 '의도된 좌표'를 중심으로 **가장 가까운 안전한 땅**을 파이썬이 실시간으로 찾아내어 좌표를 살짝 보정합니다.

### 2.2 알고리즘 작동 원리
1. **시작점 설정**: LLM이 제안한 원래의 `(X, Y)`를 큐(Queue)에 넣습니다.
2. **8방향 확장**: 현재 위치에서 상, 하, 좌, 우 및 대각선을 포함한 8방향으로 검색 범위를 넓힙니다.
3. **안전성 검증**: 각 타일에 대해 위 1.1장의 비트연산을 수행하여 `is_walkable`이 `True`인 칸을 찾습니다.
4. **최단 거리 보장**: BFS는 원형으로 퍼져나가며 탐색하므로, **가장 먼저 발견된 통행 가능 타일**이 원래 의도했던 위치와 가장 유사한 최적의 장소임이 수학적으로 보장됩니다.

**[핵심 코드: 안전 좌표 탐색]**
```python
while queue:
    x, y, dist = queue.popleft()
    if is_walkable(tile_data, x, y, ...): # 비트연산 기반 검증
        return x, y # 가장 가까운 안전 지대 발견 즉시 반환
```

## 3. 워프(코드 201) 및 플레이어 시작 지점 후처리

시스템은 맵 파일이 최종 저장되기 직전인 `Integrator` 단계에서 모든 '이동' 관련 데이터를 전수 조사합니다.

1. **최초 스폰 위치**: 게임 시작 시 플레이어가 나타나는 좌표를 `calculate_spawn_point` 로직을 통해 마을의 가장 안전한 평지로 보정합니다.
2. **장소 이동(201) 이벤트**: 맵에 배치된 모든 워프 이벤트를 스캔합니다.
    - 이벤트의 실행 내용 중 `code: 201`을 찾습니다.
    - 이동하려는 **목적지 맵의 타일 데이터**를 가져와 해당 좌표가 안전한지 비트 연산으로 확인합니다.
    - 만약 위험한 좌표라면 BFS를 통해 계산된 안전한 좌표로 `parameters[2](X)`, `parameters[3](Y)` 값을 강제 수정합니다.

## 4. 플레이 시간 기반 맵 스케일링 (Dynamic Scaling)

Re-Verse는 유저가 입력한 **의도된 플레이 시간(`target_playtime_minutes`)**을 변수로 받아 월드의 물리적 볼륨을 결정합니다.

### 4.1 플레이 시간 비례 맵 개수 산출
플레이 시간이 늘어날수록 유저가 거쳐가야 하는 중간 거점과 던전의 층수가 자동으로 확장됩니다.
- **단기 (5~7분)**: 총 3~5개 내외
- **중기 (7~10분)**: 총 4~6개
- **장기 (10~15분)**: 총 6~10개 이상

### 4.2 맵의 복잡도 및 크기 제어
시간 변수는 단순히 맵의 개수뿐만 아니라 내부 구조에도 영향을 미칩니다.
- **던전 생성기**: 플레이 시간이 길면 생성기의 `max_rooms`와 `corridor_length` 변수를 상향 조정하여 더 넓고 복잡한 미로를 만듭니다.
- **연결 밀도**: 플레이 시간이 짧으면 목적지까지의 경로를 직선화하고, 길면 우회로나 숨겨진 방을 더 많이 배치합니다.
